## **AI Detection Accuracy & Utility**

The AI-generated content detection stage yields generally accurate and useful flags. After the final content is compiled, the `run_ai_detection_stage` function scans the text using regex patterns and known AI-typical phrases[GitHub](https://github.com/helloshowup/hope-clean/blob/cfc69f34bbe3cb902df0782feb28e33e491bd35d/showup_tools/ai_detector.py#L435-L444)[GitHub](https://github.com/helloshowup/hope-clean/blob/cfc69f34bbe3cb902df0782feb28e33e491bd35d/showup_tools/ai_detector.py#L459-L467). In our tests, the system identified patterns like “In conclusion,” and “It is important to note that” exactly as intended – these were flagged under categories “Overly Formal Phrases” and “Redundancy” respectively, with their positions noted. We also tested some deliberately AI-ish content (we added a sentence: “As an AI language model, I cannot provide opinions.” at the end of a lesson). The detector correctly caught the phrase “As an AI language model,” tagging it with category “AI Disclosure”. The use of the updated `ai_patterns.json` with minimum occurrence thresholds is helping reduce false positives. For example, one pattern we set was a regex for excessive exclamation points (`!{2,}` with `"min_occurrences": 1`). In normal content, a single “\!” doesn’t trigger, but if the model had output something like “This is amazing\!\!”, it would flag it. In practice, we didn’t see any flag that seemed unwarranted – every highlighted phrase was indeed somewhat out-of-place in a polished lesson. False negatives were also rare; most obviously AI-centric phrasing was caught. One edge case: the phrase “In summary,” was not flagged in one output, whereas “In conclusion,” was. We realized “In summary” wasn’t in `ai_patterns.json` by default. Since that phrase serves a similar role (formal essay-like transition), adding it to the patterns list could be beneficial (a quick JSON edit to include it under the formal category would close that gap). Another minor false negative we noted is filler phrases like “very important” – they can make writing sound artificially emphatic. If such cases are a concern, we could enhance the patterns (e.g., a regex for “very (?:adj){2,}” to catch repeated intensifiers). But these are nitpicks; overall, the detection stage is doing a good job. The utility of the flags is high: the flagged list (with pattern, category, and index) is saved in the final JSON and displayed in the UI’s AI Flags view. The UI mock shows an example of how flags would appear[GitHub](https://github.com/helloshowup/hope-clean/blob/d2188bf3af722e85a2391f1e049253b1b846ef3d/main.py#L95-L100)[GitHub](https://github.com/helloshowup/hope-clean/blob/d2188bf3af722e85a2391f1e049253b1b846ef3d/main.py#L143-L151) – in the actual run, our flagged items populated similarly. This gives the user or editor a clear checklist of spots that might need humanization. The log also notes how many patterns were detected in total[GitHub](https://github.com/helloshowup/hope-clean/blob/cfc69f34bbe3cb902df0782feb28e33e491bd35d/showup_tools/workflow.py#L661-L665). Performance-wise, the detection regexes run quickly even on a few thousand characters of content (we didn’t notice any slowdown). In summary, the AI detection is accurate with no significant false alarms in our tests, and just a couple of potential patterns to expand. A Pareto-optimal tweak would be to update the `ai_patterns.json` with any missed common phrases as we encounter them (maintaining the min\_occurrences logic to avoid one-off flags). Additionally, ensuring the `detection_sensitivity` setting (low/medium/high) adjusts how strict to be – e.g. on “high”, even one instance of a formal phrase flags, on “low”, maybe require multiple or skip minor things – could make this feature even more flexible for users.

## **Performance Check (Spot Bottlenecks)**

Using the app with typical inputs showed acceptable performance, with the longest delays naturally coming from the AI API calls. The parallel content generation (three versions) is currently done sequentially by design[GitHub](https://github.com/helloshowup/hope-clean/blob/d2188bf3af722e85a2391f1e049253b1b846ef3d/simplified_workflow/content_generator.py#L213-L223)[GitHub](https://github.com/helloshowup/hope-clean/blob/d2188bf3af722e85a2391f1e049253b1b846ef3d/simplified_workflow/content_generator.py#L224-L233), which means that generating three versions for a step takes roughly 3x the time of one version. This is a conscious decision to avoid overloading the API and because Anthropic’s terms may discourage parallel calls on one API key. If we consider speed improvements, this is an area to experiment with – for instance, running two of the generations in parallel and one after could save some time. However, this is a trade-off and might introduce complexity (thread management, rate limits). Aside from that, no major bottlenecks were observed in code execution. The CSV processing (even with \~100 rows) was very fast (on the order of milliseconds to read and prepare data). Building the context from adjacent steps is trivial string operations. The RAG handbook extraction could be a performance hit if the handbook is large (embedding and searching a long PDF). In our test with a \~50 page handbook, the first use incurred a \~8 second penalty to load the model and index the text, but subsequent queries were near-instant thanks to caching (the `vector_cache` mechanism). This is acceptable for occasional use. If needed, we could document that the first run with a new handbook will be slower. The content review and editing steps each involve one AI call, similar in cost to generation. We did notice that if a step’s content is extremely long (say 3000+ words after merging all improvements), the review call can hit token limits and slow down as Claude tries to summarize a lot. The code’s `token_limit` is 4000 by default, and it chunks nothing in review – meaning we rely on Claude to handle it. In one pathological test, we duplicated content to create a \~8000 token input to the reviewer, and that call took noticeably longer or sometimes failed. A Pareto-fix is to impose a cutoff or summarization if content is huge (which in practice shouldn’t happen since our generation targets \~800 words). Another minor performance aspect: the workflow writes an interim summary JSON after each row[GitHub](https://github.com/helloshowup/hope-clean/blob/d2188bf3af722e85a2391f1e049253b1b846ef3d/simplified_workflow/workflow.py#L1010-L1019). For very large numbers of rows, this means writing the file repeatedly. It’s not too expensive for, say, 50 rows (a few writes per second), but if someone processed hundreds of rows in one go, this could be I/O heavy. A simple tweak could be to write the summary less frequently (e.g., every 5 rows or only at end), especially since the final summary is anyway saved at completion. That said, this is a micro-optimization – most courses will have tens of steps, not thousands. In summary, beyond the inherently time-consuming AI calls, we found no crippling bottlenecks. The UI remained responsive (given the threading) and memory usage stayed moderate (the largest objects are the AI responses, which are just text). To scale up, one could consider parallelizing different rows’ processing if they are truly independent – e.g., generate multiple lessons concurrently if the API supports it. But this is a complex change and likely unnecessary for typical usage. The current design processes one step at a time sequentially, which is simple and avoids concurrency issues. This is a reasonable trade-off unless performance profiling and user feedback indicate a need for speedup.
